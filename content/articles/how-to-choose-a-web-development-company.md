Hiring a web development company is a procurement decision and a trust decision. The work is hard to inspect before it is finished, the scope is easy to hide, and the consequences last for years.

Most buyers compare price first. That is understandable, but it is the wrong first question. Start with scope, ownership, and evidence. Then compare price.

## The one question that filters most vendors

**"Who will actually do the work, and can I meet them?"**

Some agencies sell well and subcontract the build. That can work, but you should know. Ask for the names and roles of the people who will design, build, and test your project. Ask whether the person in the sales call will be involved after signing.

If the answer is a generic "our team," ask again. You are hiring people, not a logo.

## Questions to ask before you hire

### About the project

1. What do you need from us to start?
2. What do you need from us to finish?
3. Which decisions are ours, and which are yours?
4. What is explicitly out of scope?
5. What could change the price, and how are changes approved?

### About the work

6. Show me two recent projects you built, not just designed.
7. What did you do on those projects, and what did someone else do?
8. How do you handle mobile, accessibility, and performance?
9. How do you make sure search engines can read the site?
10. What stack do you recommend, and why is it better for *this* project?

### About the process

11. What does the timeline look like, milestone by milestone?
12. How often will we see progress, and in what form?
13. What happens if a milestone slips?
14. Who tests the site before launch, and against what criteria?
15. What is the handover process?

### About ownership and aftercare

16. Who owns the domain, hosting, code repository, and analytics?
17. Will we have admin access to everything?
18. What is included after launch, and for how long?
19. What does ongoing maintenance cost?
20. What happens if we stop working together?

A good vendor answers these without defensiveness. A weak one answers with adjectives.

## The scope normalization exercise

Proposals are rarely written in the same format. Normalize them with a simple table:

| Item | Vendor A | Vendor B | Vendor C |
| --- | --- | --- | --- |
| Pages / templates | | | |
| Custom design | | | |
| CMS / editing workflow | | | |
| Content migration | | | |
| Copywriting | | | |
| Lead form + delivery | | | |
| Analytics + events | | | |
| Technical SEO | | | |
| Performance target | | | |
| Accessibility target | | | |
| Training / documentation | | | |
| Post-launch support | | | |
| Total price | | | |

If a row is blank, ask whether it is excluded or forgotten. "We can add that later" is not a scope.

## Evidence to request

- **Live URLs** of recent projects, not screenshots.
- **A short walkthrough** of one project: the problem, the decisions, the result.
- **Performance evidence** from PageSpeed Insights or Search Console, if the claim is speed.
- **A reference call** with a client who had a similar scope.
- **A written scope** with deliverables, assumptions, and exclusions.
- **A sample report** or project update so you know what communication looks like.

Claims are cheap. Evidence is not.

## Red flags

- "Guaranteed #1 rankings." No one can guarantee rankings. Google's own guidance is clear that SEO is not a one-time switch.
- "We can do everything for $500." You can buy a template for that. You cannot buy strategy, custom design, engineering, performance, SEO, and handover for that.
- No written scope or timeline.
- Full payment required upfront.
- No named team.
- No examples of live work.
- Ownership of the domain or hosting stays with the vendor.
- No plan for redirects, analytics, or launch verification.
- Pressure to decide today.
- A portfolio of beautiful screenshots with no case studies.

## Contract terms to get in writing

- Scope, deliverables, and exclusions.
- Timeline and milestone dates.
- Price, payment schedule, and what triggers each payment.
- Change request process.
- Ownership of code, content, domain, hosting, and accounts.
- Confidentiality and data handling.
- Post-launch support and warranty period.
- Termination terms and handover obligations.
- What happens if the project is delayed by either side.

If the contract is vague, the project will be vague.

## How to evaluate technical quality

You do not need to be a developer to ask useful questions.

- View the source of a live page. Is the main content there without JavaScript?
- Run PageSpeed Insights on a mobile page. Are the Core Web Vitals in the green?
- Resize the browser. Does the layout break at 375px?
- Tab through the navigation. Can you see focus states?
- Submit a form. Does it work and show a clear success message?
- Check the page title in the browser tab. Is it unique?
- Search the site with `site:example.com`. Are the right pages indexed?

These checks do not prove craftsmanship, but they reveal whether the basics are taken seriously. The [Core Web Vitals guide](/blog/core-web-vitals-2026/) explains what the numbers mean.

## A simple scorecard

Score each vendor from 1 to 5:

| Criterion | Weight |
| --- | --- |
| Relevant recent work | 25% |
| Clear scope and exclusions | 20% |
| Process and communication | 15% |
| Technical quality evidence | 15% |
| Ownership and handover | 10% |
| Price versus scope | 10% |
| Cultural fit and responsiveness | 5% |

Do not let price dominate. A cheap build that has to be redone is the most expensive option.

## Questions about SEO and performance

Ask:

- How will search engines receive the page content?
- Who writes the title and meta description for each page?
- Is structured data included?
- How will redirects be handled?
- What is the performance target, and how will it be measured?
- Who owns analytics and conversion tracking?
- What happens to old URLs?

If the answers are "we will add an SEO plugin," keep asking. Rendering, metadata, canonical URLs, and internal links are engineering decisions. Google's [Search Central documentation](https://developers.google.com/search/docs) is a useful reference for what search engines actually need.

## What good looks like

A good partner:

- Tells you what they would *not* do.
- Pushes back on a bad idea.
- Gives you a fixed scope and a realistic timeline.
- Shows progress early and often.
- Documents the handover.
- Leaves you owning everything.
- Is honest about what they can measure.

That is a lower-drama project than the one with the flashiest pitch.

## Key takeaways

- Ask who will do the work and meet them.
- Normalize scope before comparing price.
- Demand live work, references, and performance evidence.
- Get ownership, timeline, and exclusions in writing.
- Treat guaranteed rankings and suspiciously low prices as warnings.
- Choose the team you can operate with after launch.

## FAQ

### Should I hire a freelancer or an agency?

A freelancer can be excellent for a focused project with a clear scope. An agency is useful when you need multiple disciplines, coverage during holidays, and a process. The same questions apply to both.

### How many quotes should I get?

Three is usually enough. More than that wastes everyone's time unless the scopes are very different. Compare normalized scope, not just the bottom line.

### Do I need a local company?

Not for most digital work. Time-zone overlap and communication matter more than geography. For local SEO and in-person workshops, a local partner can help.

### What if the cheapest quote is from a friend?

Friendship is not a scope. Use the same written process. A clear contract protects the relationship.

### How do I protect myself from a bad build?

Pay in milestones, keep ownership of accounts, require a written scope, test the site before final payment, and ensure you receive documentation and credentials at handover.
